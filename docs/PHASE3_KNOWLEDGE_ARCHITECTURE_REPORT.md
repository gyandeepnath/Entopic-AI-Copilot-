## 0. The declaration this report has to open with

Everything below was **measured by loading and querying the actual knowledge
base**, not inferred from reading. The method is stated for each claim so it
can be re-run.

That matters more than usual here, because during this phase **six of my
measurement scripts produced confident, entirely false findings** before I
checked them. The worst: I concluded that 23 conditions — including Chemical
Eye Burn and Open Globe Injury — could never fire, because 13 required tokens
were "unproducible". I ran the engine before writing it down. Chemical Eye Burn
fires correctly. My scan had simply omitted `js/data-model.js` from the list of
files that produce tokens.

Had I reported that, the founder would have spent a day investigating working
emergency logic. **The rule stands: a finding is not a finding until the probe
that produced it has been checked.** Every number below survived that check.

I am also not a clinician. Where a question is clinical, this report presents
the measurement and stops.

## 1. The knowledge architecture as it actually is

### 1.1 Storage and shape

Knowledge lives in `knowledge/` as **21 plain JavaScript files** containing
object literals. No database, no build step, no serialisation format. The
files are loaded as ordered `<script>` tags before any application code.

| Layer | Files | Purpose |
|---|---|---|
| **Clinical content** | `surface`, `corneal`, `retina`, `neuro`, `binocular`, `refractive`, `glaucoma`, `anterior`, `lens`, `expansion` | The 394 conditions |
| **Vocabulary** | `token-registry` (7,980 ln), `token-dictionary`, `finding-token-map` | 575 tokens, aliases, finding→token maps |
| **Coding** | `icd-map` (910 ln) | ICD-10 assignment |
| **Narrative** | `condition-info` (4,116 ln) | Human-readable per-condition text |
| **Classification** | `age-classification`, `common-conditions`, `verified` | Age bands, 109 common conditions, sign-off state |
| **Scales** | `clinical-scales` | AREDS, with citation and verbatim source |
| **Assembly** | `loader` (385 ln) | Merges, indexes, stamps review status |

### 1.2 Lifecycle

```
  AUTHORED            ASSEMBLED                CONSUMED
  ────────            ─────────                ────────
  domain file    →    loader.js IIFE      →    KNOWLEDGE_ALL (global)
  (object         ·  merges 10 sources          ├→ engine.js  (scoring)
   literal)       ·  stamps review_status       ├→ ui-advisory (display)
                  ·  applies ICD map            ├→ kb-review   (sign-off)
                  ·  applies age brackets       ├→ quiz / OSCE / simulation
                  ·  builds route + token       └→ validation workspace
                     indexes
        ↑                                              │
        │                                              ▼
   KB editor (admin, in-app)  ←──  kb_signoffs  ←  clinician verifies
   kb-remote (cloud bundle)                         (attestation + hash)
```

Three properties of this lifecycle are genuinely good and should be protected:

- **Assembly is deterministic and happens at load.** Same files, same
  `KNOWLEDGE_ALL`, every time.
- **It fails closed.** A condition with no `review_status` is stamped
  `NEEDS_CLINICAL_REVIEW` (ADR-009). Absence of evidence of review is treated
  as evidence of absence.
- **Sign-offs are fingerprinted.** A verification is bound to a hash of the
  condition's clinical fields, so editing the content invalidates the sign-off
  rather than silently inheriting it.

### 1.3 Ownership — measured

| Artefact | Who can change it | How |
|---|---|---|
| Condition content | Founder | In-app KB editor, or the source file |
| Review status | Founder | Sign-off workflow (hash-bound) |
| Age brackets | Founder | Admin screen, protected store |
| Token registry | Engineer | Generated by `tools/gen-token-registry.js` |
| ICD map | Engineer | Source file |
| Everything else | Engineer only | Source file |

**The gap:** a domain specialist or a university cannot contribute anything
without either the founder's admin account or a pull request. There is no
contribution path for the people most able to improve the content.

## 2. The schema, and what it does not model

Every condition carries exactly these fields (verified across all 394):

```
name  route  req[]  sup[]  con[]  temporal[]  tests[]  exclusions[]
icd  icd_label  icd_status  domain  review_status
urgent (66)   age_bracket (15)   age_bracket_status (15)
```

### What is modelled well
`Disease` as a first-class entity, with `Sign`/`Symptom`/`Finding` unified as
**tokens** — a single flat vocabulary of 575 terms. That unification is a real
strength: one matching mechanism, one registry, one place to audit.

### What is NOT modelled at all

| Concept | Status | Consequence |
|---|---|---|
| **Evidence / citation** | **Absent — 0 of 394 conditions carry any source, citation, reference or evidence field** | Nothing in the knowledge base can answer "why does this rule exist?" |
| Severity / stage | Absent | "Cataract" cannot express NS2 vs NS4; staging lives in condition names |
| Risk factor | Conflated with `sup` | A risk factor and a clinical sign score identically |
| Complication | Absent | No `leads_to` relationship |
| Procedure / treatment | Absent | Management is free text in the visit, not knowledge |
| Follow-up interval | Absent | No recall guidance is derivable |
| Outcome | Absent | Nothing to calibrate scores against |
| Condition→condition relations | Absent | No hierarchy, no "is a form of", no differential grouping |
| Laterality rules | Absent | Nothing states that bilateral disc oedema differs from unilateral |

**The single most important finding of Phase 3 is the first row.** The
knowledge base has no evidence layer whatsoever. Not thin — absent.

### Severity/stage: the workaround is visible in the names
89 of 394 condition names contain parentheses and 5 use a dash separator
("Dry Eye Disease - Evaporative (MGD)", "Blepharitis - Posterior (MGD)").
Sub-typing that should be structured is encoded in strings.

## 3. Terminology audit

| | |
|---|---|
| Registry entries | **575** |
| Tokens actually used by conditions | **481** |
| Registered but used by no condition | **94** |
| KB tokens missing from the registry | **0** ✓ |
| Tokens in `lower_snake_case` | 468 |
| Tokens containing uppercase | **13** |
| Tokens with spaces or hyphens | 0 ✓ |

**Consistency is good but not complete.** The convention is clearly
`lower_snake_case`, and 13 tokens break it — all of them preserving a clinical
abbreviation: `TBUT_reduced`, `RAPD_positive`, `CNVM`, `OCT_edema`,
`MLF_lesion_sign`, `NPC_receded`, `reduced_PFV`, `high_ACA_ratio`,
`RNFL_thinning`, `gonioscopy_NVA`, `stellate_KPs`, `B_scan_ultrasound`,
`CT_orbits_imaging`.

That is a defensible choice, not a mistake — `RAPD` is not `rapd` to a
clinician. But it is **undocumented**, so the next author cannot tell whether
to write `RNFL_thinning` or `rnfl_thinning`. The convention should be written
down, not changed. Renaming would be a behaviour change for no clinical gain.

**The 94 unused registry entries** are partly schema keys leaking into the
count (`req`, `sup`, `type_hint`, `usage`) and partly genuinely orphaned
vocabulary. They are harmless but they inflate the apparent vocabulary by 20%.

**No international terminology binding.** Nothing maps to SNOMED CT, LOINC or
UMLS. ICD-10 is present on all 394 — good — but ICD-10 is a billing and
statistics classification, not a clinical ontology, and cannot carry the
relationships this knowledge base will eventually need.

## 4. Rules audit

The rule model is: a condition matches when its `req` tokens are present;
`sup` raises the score; `con` lowers it; `temporal` and `tests` refine.

| Property | Count | Reading |
|---|---|---|
| Conditions with `req` | 394 / 394 | Every condition has a trigger ✓ |
| Conditions with `sup` | 394 / 394 | ✓ |
| Conditions with **no** `con` | 17 | Nothing argues against them |
| Conditions with **no** `tests` | **144** | The "check next" loop has nothing to offer |
| Conditions with **no** `exclusions` | **382** | The exclusion mechanism is almost unused |
| Conditions with `temporal` | 392 | ✓ |

**The exclusions mechanism exists and is used by 12 conditions out of 394.**
Either exclusion is rarely clinically appropriate, or 370 conditions are
missing exclusion logic. That is a clinical question, not an engineering one.

**144 conditions offer no discriminating test.** The refinement loop —
arguably the best thing in the product — is silent for 37% of the knowledge
base.

### Two flag/route mismatches, verified
`Horner Syndrome` (route=neuro) and `Scleritis` (route=anterior) carry
`urgent: true` while not being routed as urgent. **This is probably correct
rather than a bug** — `route` is a clinical category and `urgent` is a safety
flag, and they are orthogonal by design. But nothing documents that they are
orthogonal, and 61 of the 63 urgent conditions have both. **⚠ Worth the
founder confirming**, because if they are meant to agree, two urgent conditions
are mis-routed.

### 56 ICD codes are shared by more than one condition
e.g. `H01.009` on three conditions, `H02.889` on two. Mostly "unspecified"
codes, which is legitimate ICD practice. But it means ICD cannot be used as a
condition identifier, and any future registry or research export keyed on ICD
will silently merge distinct conditions.

## 5. Evidence — the finding that dominates this phase

**Zero of 394 conditions carry any evidence field.** Verified by inspecting
every key on every loaded condition: the field set is fixed and contains no
`source`, `citation`, `reference`, `evidence`, `guideline` or `grade`.

This means the knowledge base cannot answer, for any of its 394 conditions:

- Why does this rule exist?
- What is it based on?
- Which guideline, which edition, which year?
- Who decided that `high_iop` supports this condition rather than requires it?
- Can it be challenged, and against what?

**The contrast within the repository is instructive.** `clinical-scales.js`
does it properly: the AREDS scale carries a `source` (citation, DOI/PMID) and a
`verbatim` field holding the exact sentence from the source. One file in the
knowledge base has an evidence model. The other twenty do not.

This is also the reason the sign-off campaign is harder than it looks. A
clinician verifying condition #200 has nothing to verify *against* except their
own recall — there is no stated basis to agree or disagree with. Adding an
evidence field would make sign-off faster as well as more defensible.

**This is the top recommendation of Phase 3 and it is not close.**

## 7. Maintainability

**Can one disease be modified safely?** Yes. Conditions are independent object
literals; editing one cannot affect another. The engine is data-driven, so a
change takes effect with no code change. Tests catch structural breakage.

**Will an update break reasoning?** Possibly, and nothing measures it. There is
no "what would this edit change?" preview — a clinician editing `req` on a
common condition cannot see that it would alter 40 differentials.

**Can non-programmers update knowledge?** The founder can, through the in-app
KB editor. Nobody else can.

**Can domain experts or universities contribute?** **No.** This is the largest
governance gap and is addressed in the Governance Manual.

## 9. The final questions, answered plainly

**Would I trust this knowledge to support real clinicians?**
As an advisory prompt beside a clinician who knows the subject — yes, with the
verification banner it now carries. As a source a clinician relies on — no, and
not because it is wrong, but because nobody can tell whether it is right.

**Would I trust it for students?**
Yes, with supervision, and it is genuinely good for this: 394 narratives, a
transparent reasoning trail, and 109 conditions marked common. A student
learning *how to reason* is well served. A student learning *facts* from
unverified content is not.

**Would I trust it in research?**
Not yet. Without evidence provenance and with ICD codes reused across
conditions, findings could not be defended.

**Would I trust it as the foundation of future AI?**
**Yes — this is its strongest suit.** A deterministic, tokenised, structured
knowledge base with per-condition narrative is close to ideal for grounding and
verification. Add citations and it becomes genuinely valuable: the thing that
tells a model when it is wrong.

**What is missing?** Evidence, severity/staging, condition relationships,
outcomes, follow-up intervals, and a contribution path for anyone but the
founder.

**What should be rewritten?** Nothing. No structural rewrite is warranted —
that is a real compliment to how it was built. The work is additive.

**What should never change?**
1. Knowledge stays **data, not code** (ADR-005).
2. The loader **fails closed** on unknown review status (ADR-009).
3. Sign-offs stay **hash-bound** to content.
4. `clinical-scales.js` keeps its `source` + `verbatim` model — it is the
   template everything else should follow.
5. Nothing is invented. `NEEDS_CLINICAL_REVIEW` over a plausible guess, always.

## 10. How far from world-class?

| Milestone | Effort |
|---|---|
| Evidence field + 50 highest-impact conditions cited | ~120 h + clinical time |
| All 394 clinically verified | ~20 h of the founder's time |
| Severity/staging modelled | ~80 h |
| Condition relationships (is-a, leads-to, differential-of) | ~120 h |
| SNOMED CT binding | ~200 h |
| Contribution + peer-review workflow | ~150 h |
| Outcome linkage and calibration | ~200 h |
| **World-class ophthalmic knowledge foundation** | **~900 h + sustained clinical input** |

**Entopic is roughly 40% of the way to a world-class knowledge foundation.**
The structure is largely right and does not need rebuilding. What is missing is
the evidence layer, the relationships, and — above everything — a clinician's
signature on all 394 conditions.

Two of those three are engineering. The third is 20 hours the founder has not
yet spent, and it is worth more than the other two combined.
