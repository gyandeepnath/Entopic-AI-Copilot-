## What was wrong, and what I changed

### 1. Passwords were stored in plaintext  ▲ the important one

`doSetup()` wrote `password: pw` straight into local storage, and `doLogin()`
compared with `===`. Anyone who opened the store, copied the device, or got hold
of an exported backup could read every user's actual password.

That matters beyond Entopic: people reuse passwords, so leaking one in plaintext
harms that person on other services.

**Fixed** (`js/auth-crypto.js`): passwords are now salted with a
cryptographically random 16-byte salt and stretched with **PBKDF2-SHA-256,
120,000 iterations**, via Web Crypto — which works on `file://` because a local
page is a secure context, so this stays fully offline with no dependency.
Comparison is constant-time. Existing accounts are migrated automatically on
their next sign-in: the plaintext is checked once, replaced with a hash, and
erased. Verified in a real browser — a legacy account went from plaintext to
hashed on login and the old password no longer appears anywhere in the store.

**What this does not do, stated plainly:** Entopic is a client-side app. Someone
with the device and the source can still bypass the sign-in screen. This is not
a claim of real authentication — that arrives with the cloud backend, where
verification happens server-side. What hashing buys is that *a leaked store or
backup no longer reveals anybody's password*.

The Admin panel now shows how many accounts still hold a plaintext password, so
the state is visible rather than assumed.

### 2. Signing out dropped you on the wrong form

After creating an account and signing out, the sign-in fields were still hidden
and you landed on "Create new account" with no way back except a reload.
`doLogout()` now restores the sign-in view and clears the fields.

### 3. `young_age` meant "under 18" and was being used for adults

See `knowledge/age-classification.js`. Three brackets now exist:

| token | rule |
|---|---|
| `paediatric_age` | under 18 |
| `young_adult_age` | 18 – 39 |
| `young_age` | under 18 — **deprecated, rule unchanged** |

`young_age` keeps its exact old behaviour, so **no differential shifts for any
condition that has not been reclassified**. Only 15 conditions are pre-set — the
ones whose *name* literally states infancy or childhood (congenital, infantile,
neonatorum, of prematurity, juvenile, amblyopia). Even those are provisional.

**83 conditions still need your clinical judgement**, including Keratoconus,
Optic Neuritis and Idiopathic Intracranial Hypertension. Those are
epidemiological calls, not text-matching, so they are yours. There is now a
one-click review screen in the Admin panel with an Export button that writes a
file for baking the decisions into the build.

One trap worth recording: *Congenital* Hypertrophy of the RPE is congenital by
name but found at any age, so it was deliberately **not** auto-classified.

### 4. Two knowledge-base loaders had silently drifted apart

The test harness has two loaders. `tools/lib/load-kb.js` was missing three
knowledge files that `tools/lib/load-engine.js` loads, so half the test suite
was reasoning about a differently assembled knowledge base from the other half.
Aligned, and a test now fails if they diverge again.

### 5. A NUL byte in source

A raw `\0` had landed in `js/auth-crypto.js`, which makes `grep` treat the file
as binary and breaks diff tooling. Fixed, and the audit now fails on any NUL
byte in source.

### 6. Documentation claimed 130 conditions; the build has 394

`ARCHITECTURE.md` was ~3× out of date on every count, and still listed
"ICD codes never populated" as an open gap when all 394 conditions now carry
one. Corrected, and the audit now fails if the stated count drifts from reality
again.

### The one remaining warning

**29 source files are not referenced by any test** — mostly UI modules
(`clinics-ui.js`, `certificates-ui.js`, `assignments-ui.js`, `drawing-guide.js`).
They are exercised in the browser checks but have no unit tests. Not a defect;
it is where the safety net is thinnest, and it is the honest next place to
invest.

## Standing limits you should know about

These are **not bugs** — they are the shape of a local-first app, and they are
listed so nothing is implied that isn't true.

1. **The sign-in screen is a convenience lock, not access control.** Anyone with
   the device can reach the data. Multi-user isolation needs the backend.
2. **The admin gate uses a light hash** (`djb2`) rather than PBKDF2, and the
   default hash is in the source. Fine for a local founder lock, not for
   anything else.
3. **All clinical content is provisional** until you sign it off: 257 conditions
   carry `NEEDS_CLINICAL_REVIEW`, 0 verified so far. The Review Queue is where
   that happens and it exports your sign-offs into the build.
4. **The backup file is sensitive.** Credentials in it are hashed, but it still
   contains patient records in the clear. It is your data on your disk — treat
   the file accordingly.
5. **Storage is `localStorage` + IndexedDB for files.** Roughly 5–10 MB for
   records. Fine for a single clinic; the backend is what makes it unbounded.
