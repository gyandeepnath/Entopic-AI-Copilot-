# Entopic — System Architecture & Scaling Blueprint

**Document version:** 1.0
**Covers build:** Entopic v1.0.0 (33 files, ~12,290 lines, 130 conditions across 9 domains)
**Purpose:** A ground-truth teardown of everything in the current system, followed by a target architecture that keeps the same UI and concept but rebuilds the foundations for scale, onboarding, a stable backend, an independent continuously-looping diagnostic engine, and a trustworthy evidence-based knowledge base.
**Standing constraint:** Entopic is advisory decision-support. Every diagnostic output requires clinical correlation. Nothing here changes that contract.

# PART I — THE CURRENT SYSTEM, IN DEPTH

## 1. What Entopic is, and the design philosophy baked into the code

Entopic is a **single-page, browser-only ophthalmic exam copilot**. There is no server, no build step, no framework. Open `index.html` in a browser and the whole application runs client-side, persisting to `localStorage`.

Three design commitments are visible throughout the source and should be preserved:

1. **Offline-first.** The diagnostic engine never touches the network. This is a genuine strength for tertiary and rural Indian settings with unreliable connectivity, and it is the right default.
2. **The engine diagnoses; the LLM does not.** `claude.js` is explicitly firewalled: the Claude API is used only for (a) interpretive remarks *downstream* of the engine and (b) speech-to-data parsing. It never scores conditions or generates differentials. This is the correct separation for a clinical tool — the reasoning is deterministic, inspectable, and reproducible.
3. **Zero evidence = zero output.** The engine refuses to guess. With no clinical inputs it emits an empty differential rather than a speculative one.

These three commitments are the product's spine. Everything in Part II keeps them.

## 2. Runtime and load model

There is no bundler. The application is assembled by **ordered `<script>` tags** in `index.html`, and every module communicates through **global variables** (`var` in the global scope, `"use strict"` per file). Load order is dependency-critical and is enforced only by the order of those tags:

```
Knowledge base (data, no deps)
  → loader.js (assembles KB into unified structures)
  → data-model.js (schema + clinical constants)
  → storage.js (persistence)
  → engine.js (reads KB + data model)
  → UI renderers (read engine + data model)
  → feature modules (speech, Claude, drawing, calculators, intake, advisor)
  → app.js (LAST — wires auth, routing, autosave)
```

**Global state** lives in `app.js` as five variables:

- `CU` — current user object
- `CP` — current patient ID
- `CV` — current visit ID
- `P` — current patient object (the working copy)
- `V` — current visit object (the working copy — the single most important object in the app)
- `API_KEY` — the Claude key, if configured

The entire UI is a function of `P` and `V`. Every interaction mutates `V` (or `P`), re-runs the engine, and re-renders three panels. This is effectively a hand-rolled reactive loop without a framework.

**Rendering model.** UI is generated by string concatenation into `innerHTML`. Page renderers (`pgDemo`, `pgCC`, `pgVA`, …) each return an HTML string for one exam step; `renderMain` dispatches to the right one based on `V.step`. `renderSidebar` draws the 22-step navigation; `renderAdvisory` draws the right-hand diagnosis/alert/nudge panel. There is no virtual DOM and no component model — re-rendering replaces whole panels.

**Consequence to keep in mind:** because state is global and rendering is full-panel `innerHTML`, the app is simple and fast for one user but has no isolation, no reactivity primitives, and no way to update a sub-region without redrawing its container. This is fine at current scale and is one of the things Part II modernizes *without changing the visible UI*.

## 3. The data model (`data-model.js`) — the master schema

This file is the backbone. It defines the visit schema and all clinical reference constants.

### 3.1 The 22-step exam flow (`STEPS`)

Registration → History → Examination → Investigations → Assessment → Management → Documentation, as 22 ordered steps (`demographics`, `chief_complaint`, `hx_ocular`, `hx_medical`, `hx_family`, `va`, `refraction`, `dilation`, `slit_lamp`, `iop`, `pupil`, `motility`, `bv`, `gonioscopy`, `fundus`, `neuro`, `investigations`, `diagnosis`, `plan`, `coding`, `report`, `prescription`). This ordered clinical workflow is a core part of the product identity and stays.

### 3.2 `blankVisit()` — the visit object `V`

This is the authoritative schema for a single encounter. It is a deep, well-structured object with sub-objects for every station:

- **Complaint:** `cc` (free text), `foldarq` (FOLDARS mnemonic fields), `symptoms` (array of tokens), `temporal` (`onset`/`duration`/`course`).
- **History:** `hxO` (ocular, incl. `flags[]`), `hxM` (medical, incl. structured booleans `dm`/`htn`/`autoimmune`/… and `drug_list[]`), `hxF` (family booleans), `hxS` (social).
- **Examination:** `va` (uncorrected/aided/pinhole/BVA/near per eye), `rx` (full sphero-cylindrical Rx + PD + retinoscopy + autorefraction), `dil`, `sl` (slit lamp: per-eye lids/conj/cornea/VH/cells/flare/iris/LOCS/TBUT/Schirmer + `findings[]` + `drawings[]`), `iop` (per eye + method + CCT + corrected + diurnal), `pupil` (sizes/reactions/RAPD), `mot` (versions/ductions/saccades/pursuits/Hirschberg/nystagmus), `bv` (cover test, NPC, four vergence ranges each with blur/break/recovery, AC/A, accommodative amplitude, MAF/BAF, NRA/PRA, MEM, stereo, Worth-4-dot), `gon` (gonioscopy per quadrant per eye), `fun` (fundus per eye: media/CD/NRR/disc/margin/macula/vessels/periphery/vitreous + `findings[]` + `drawings[]`), `neuro` (color/CVF/Amsler).
- **Investigations:** `inv` (OCT RNFL/CST/GCL, VF MD/PSD/pattern, topography, pachymetry, photos).
- **Questionnaire:** `osdi`.
- **Assessment/Management:** `plan` (management/follow-up/education/referral).
- **Engine outputs (written back into V):** `dxList`, `alerts`, `nudges`, `sugTests`, `engineLog`.
- **Registry:** `encounter` (the anonymized, PII-stripped projection).

This schema is genuinely good — it is comprehensive, clinically literate, and already separates raw inputs from engine outputs. Part II keeps it almost entirely, adding stable IDs and versioning.

### 3.3 Clinical constants and norms

The file also encodes the domain knowledge that makes the tool feel professional: Snellen/LogMAR/N-notation acuity ladders with LogMAR equivalents; **age-adaptive chart recommendations** (`AGE_CHART_MAP`, e.g. preferential looking / Teller / Cardiff for 0–2); refraction value ranges generated programmatically; dilation drug list; **Morgan's norms** for binocular vision; tonometry methods; temporal pattern vocabularies; **12 symptom categories with 150+ symptoms** (`SYM_CATS`), each keyed by an engine token; expanded slit-lamp and fundus finding menus (`SL_FINDINGS`, `FUN_FINDINGS`); structured medical/family/ocular-history flag lists; **Hofstetter's formula** for age-expected accommodative amplitude; and `getAgeBracket` for de-identified reporting.

`blankPatient()` is deliberately minimal (identifiers + demographics) — clean separation of the person from the clinical encounter, which matters for Part II's PII handling.

## 4. Storage layer (`storage.js`)

A thin CRUD layer over `localStorage`, namespaced with the `entopic_` prefix, storing four JSON blobs: `users`, `patients`, `visits`, `settings` (plus `apikey` and a `registry_queue`).

- **Read/write** wrapped in try/catch; write path handles `QuotaExceededError` by alerting the user to export and clear. (This is the 5 MB ceiling showing through.)
- **Autosave:** `doSave()` writes the current `V` into its visit record and merges `P` fields back into the patient record; driven by a timer in `app.js` (default 20 s) and on navigation. A "Saved" indicator flashes.
- **Visit lifecycle:** visits carry `status` (`in_progress` → `completed`), timestamps, and helpers for "last visit" and "previous completed visit" (the hook for visit-to-visit comparison).
- **Backup:** `exportAllData()` serializes everything to a downloadable JSON; `importData()` restores it (with a destructive "replace all" confirm).
- **Anonymized encounter builder:** `buildAnonymizedEncounter()` strips PII and retains age bracket, sex, symptom/finding/diagnosis tokens, a coarse `treatment_category` (via keyword bucketing in `categorizeTreatment`), referral type, and completeness — queued locally on visit completion **if registry opt-in is set**. This is the seed of the clinical-validation pipeline that Part II formalizes.

**Structural note:** all visits for all patients live in one array under one key. Every save rewrites the entire array. This is O(n) per save and shares a single 5 MB budget across the whole clinic — fine for a demo, a wall for onboarding.

## 5. The knowledge base

The KB is split across **9 domain files** plus three infrastructure files, assembled at load time by `loader.js`.

> **Adding conditions?** Follow `docs/KB_AUTHORING_CHECKLIST.md` — the
> definition-of-done for every new condition. In short: it must arrive with its
> **engine inputs** (reachable `req` token, rule-out power, surfaces on its own
> evidence, no cross-conflict, review-flagged) **and** its **"About" content**
> (auto-derived from those same tokens by `knowledge/condition-info.js`, or a
> richer hand-authored `CONDITION_INFO` entry for common conditions). The two are
> generated from the same tokens so they stay in lock-step; the `kb-expansion`
> test gate enforces both. Reference prose is display-only and never feeds
> scoring.

### 5.1 The shape of a condition

Every condition is a plain object. Example (POAG, from `glaucoma.js`):

```js
{
  name: "Primary Open Angle Glaucoma (POAG)",
  route: "glaucoma",
  req:  ["field_defect"],                 // required tokens (+3 each)
  sup:  ["high_iop","increased_cd", ...], // supportive tokens (+1 each)
  con:  ["acute_pain","shallow_ac"],      // contradicting tokens (-3 each)
  temporal: ["chronic","progressive"],    // time-course fit (±0.5)
  tests: ["visual_field_defect", ...],    // suggested tests (display only)
  exclusions: ["acute_angle_closure"]     // conditions this suppresses
}
```

The **`req`/`sup`/`con`** triad — required / supportive / contradicting tokens, updated continuously with a visible evidence trail — is the genuine novelty and the heart of the patent. It stays. Everything in Part II is about making it rigorous, coded, and evidence-graded.

**Domain counts (verified):** Surface & Lids 29, Cornea 25, Retina 22, Neuro-Ophthalmic 13, Binocular Vision 10, Refractive 5, Glaucoma 8, Anterior/Uveitis 10, Lens 8 — **130 conditions**, of which 17 are flagged `urgent`.

### 5.2 The three token layers

The token vocabulary is currently minted in **three independent places** with no reconciliation:

1. **`token-dictionary.js`** — maps **183** engine tokens to natural-language aliases (`"dryness": ["dry","dry eyes",…]`). Used by search, speech, and free-text inference to turn words into tokens.
2. **`finding-token-map.js`** — maps **171** selectable clinical findings (display strings like `"Ciliary flush"`) to the engine tokens they activate (`["redness","pain","photophobia"]`). This is the bridge from what a clinician clicks to what the engine reasons over.
3. **The condition files themselves** — every `req`/`sup`/`con`/`temporal`/`tests` value is a token.

Additionally, the **engine mints tokens directly** in two more places: `parseComplaintText` (regex → tokens) and the auto-derivation block in `collectTokens` (measurements → tokens like `high_iop`, `increased_cd`, `narrow_angle`).

**This is the single most important structural fact in the codebase.** There are five token producers and no registry. (See §10 and Appendix B for the audit: 512 tokens are referenced by the KB, 183 are defined in the dictionary.)

### 5.3 `loader.js` — assembly and derived indexes

At load, `loader.js`:

- Registers each `KB_*` array into `KNOWLEDGE_DOMAINS` (domain label → conditions).
- Flattens all domains into one array **`KNOWLEDGE_ALL`**, backfilling missing fields to empty arrays and tagging each condition with `_domain` and `_index`.
- Builds derived indexes the engine and UI rely on: `KB_ROUTES` (route → condition names), `KB_TOKEN_STATS` (which conditions use each token, split by req/sup/con), and **`KB_EXCLUSION_MAP`** (condition name → its exclusions).
- Exposes helpers: `getConditionsByRoute`, `getUrgentConditions`, `findCondition`, `conditionsRequiringToken`.

This is a clean, sensible assembly step. It is the natural place to later insert **validation** (Part II): fail the load if any token is undeclared or any exclusion target is unresolvable.

## 6. The diagnostic engine (`engine.js`) — the full pipeline

`runDiagnosticEngine()` runs on **every data change**. It is a 12-stage pipeline. Below is what each stage actually does.

**Stage 1 — Collect (`collectTokens`).** Reads all of `V` and `P` and emits tokens from **nine sources**: (1) selected symptoms (already tokens), (2) free-text CC via `parseComplaintText`, (3) temporal selections, (4) slit-lamp findings via the finding-map, (5) fundus findings via the finding-map, (6) medical-history booleans, (7) ocular-history flags, (8) family history, and (9) a large **auto-derivation** block that turns measurements into tokens: age bands; IOP thresholds (`high_iop` >21, `IOP_very_high` >30); CCT (`thin_cornea` <520); Van Herick (`narrow_angle`/`shallow_ac` ≤2); AC cells; RAPD; NPC (`NPC_receded` ≥6); cover-test phorias parsed by regex (`exo_near`/`eso_near`/… >6Δ); AC/A; accommodative amplitude vs Hofstetter minimum; flipper rate; vergence ranges; refraction (`myopia`/`hyperopia`/`astigmatism`/anisometropia/add); VA-improves-with-correction; C/D (`increased_cd` ≥0.6, asymmetry >0.2); NRR/disc descriptors; motility; TBUT/Schirmer/LOCS; neuro (color/CVF/Amsler); and investigations (OCT RNFL <80, VF MD thresholds). This block is where a lot of clinical intelligence lives, and where a lot of hard-coded constants live.

**Stage 2 — Parse free text (`parseComplaintText`).** ~40 regex rules mapping phrases to tokens (`/blur|fuzzy|hazy/ → blur`, `/flash/ → flashes`, etc.). Serviceable but brittle: no negation handling ("no pain" still yields `pain` unless the regex is written to exclude it), no synonym coverage guarantee, English-only.

**Stage 3 — Normalize.** Dedupe.

**Stage 4 — Temporal weighting.** Injects bias tokens (`sudden_onset`/`acute` → `acute_bias`; `gradual`/`chronic`/`progressive` → `chronic_bias`).

**Stage 5 — Decision-tree gating (`applyDecisionTree`).** Hard clinical override rules that surface specific conditions regardless of scoring: flashes+floaters → retinal tear/detachment/PVD; field loss → RD; pain+photophobia → anterior inflammation; sudden vision loss → CRAO/AION; severe pain+halos → acute angle closure; bilateral disc swelling → papilledema; ptosis+diplopia → CN3 palsy. This is the safety net and it is correctly independent of the probabilistic layer.

**Stage 6 — Route selection (`selectRoutes`).** Decides which domains to evaluate at all, so the engine doesn't score all 130 conditions blindly. Routes: urgent, neuro, retina, anterior, surface, binocular, refractive, glaucoma, lens, or `general` fallback.

**Stage 7 — Scoring (`scoreCondition`).** For each condition on an active route (or gated): +3 per matched required token, +1 per supportive, −3 per contradicting, ±0.5 temporal. Normalizes against max-possible, then applies multiplicative penalties (missing required ×0.7 then ×0.5; any contradiction ×0.6; <2 total tokens ×0.5), caps to [0,1], and **forces 0 if no required token matched**. Gated conditions get a ×1.3 boost.

**Stage 8 — Exclusions (`applyExclusions`).** Intended to drop conditions that a high-scoring condition rules out. **This is currently broken** — see §10.

**Stage 9 — Evidence (`generateEvidence`).** For each condition, builds the human-readable trail: which tokens **matched**, which required tokens are **missing**, which are **contradicted**, plus suggested tests and a confidence band. This transparent trail is the differentiator (and, as you've noted, the anchoring-bias risk to manage).

**Stage 10 — Alerts (`computeAlerts`).** Hard safety rules independent of diagnosis: sudden vision loss, flashes+floaters, curtain vision, pain-on-movement, metamorphopsia, IOP tiers (>21/>30/>40), RAPD, Van Herick ≤2, diabetic-without-fundus, bilateral disc edema, hypopyon, rubeosis. Correct design — safety is not gated behind probability.

**Stage 11 — Nudges (`computeNudges`).** Suggests the next exam step from the top conditions' routes and their missing evidence ("Measure IOP", "Perform gonioscopy", "Cover test"). This is the workflow-guidance layer.

**Stage 12 — Log.** Records each run (token/route/result counts, top Dx, top score, alert count), keeps the last 50, persists the last 10 into `V.engineLog`.

Finally, results are sorted (urgent floats up when score >0.2), the top 8 become `V.dxList` with a reasoning string, and alerts/nudges are written back to `V`.

**Assessment of the engine.** The architecture is sound and the intent is right: deterministic, evidence-carrying, safety-gated, workflow-aware. The weaknesses are specific and fixable (§10): universal scoring constants, a broken exclusion matcher, single-list competition, and dependence on an unmanaged token vocabulary.

## 7. The interpretive layer (`claude.js`)

A generic `callClaudeAPI` wrapper (direct browser call, debounced) plus `requestInterpretiveRemarks` → `buildClinicalSummary`, which assembles a compact clinical summary and the engine's differential and asks the model for **3–5 sentences of interpretation only** — explicitly instructed not to diagnose or repeat the list. Remarks render in the advisory panel with an "advisory only" disclaimer. The engine runs fully without a key. This firewall is exactly right and should be preserved verbatim in principle.

## 8. Clinical calculators, intake, medications, spectacles

- **`risk-calc.js`** — three literature-based calculators that consume data already in `V`, so they add no extra input burden:
  - **OHTS** — 5-year POAG conversion risk from age/IOP/CCT/vertical-C-D/PSD, additive points → Low/Moderate/High/Very-High bands with management text. (A simplified, points-based reimplementation of the published model.)
  - **ETDRS** — diabetic-retinopathy severity from fundus findings (no-DR → mild/moderate/severe NPDR → PDR), with screening intervals and a macular-edema modifier. Currently grades both eyes together (a known simplification).
  - **AREDS2** — AMD progression category from drusen/RPE/GA/CNV findings, with supplement indication.
- **`smart-intake.js`** — plain-language pre-visit questionnaire plus **OSDI** (12 items, standard severity bands) and **SPEED** dry-eye instruments, auto-populating CC/FOLDARS/symptom tokens.
- **`medication-checker.js`** + **`knowledge/medications.js`** — a systemic-drug → ocular-side-effect database (steroids → PSC/IOP/CSCR; hydroxychloroquine/chloroquine → maculopathy; alpha-blockers → IFIS; etc.) with alias matching, a review panel, and a `getMedicationTokens` bridge into the engine.
- **`spectacle-advisor.js`** — lens index / design / coating recommendations from Rx and lifestyle.
- **`drawing.js`** — canvas overlay for slit-lamp and fundus sketches, with anterior/fundus templates, saved into `V.sl.drawings` / `V.fun.drawings`.

These are strong, self-contained clinical features. In Part II they become **plugins over the same engine and registry** rather than bespoke modules, so their embedded thresholds are governed by the same evidence process.

## 9. The reasoning UI (`ui-advisory.js`, `ui-flowmap.js`)

- **Advisory panel** — live differential (name, confidence, evidence chips), alerts, nudges, medication alerts, and (optionally) AI remarks. This is the clinician-facing output of the engine.
- **Flow map** — a layered visualization that replays the engine's own reasoning: `renderTokenLayer → renderRouteLayer → renderGateLayer → renderScoringLayer → renderExclusionLayer → renderResultLayer`. This is effectively a **built-in audit trail / glass-box view** of a single engine run, and it is a real asset: it is the honest answer to "why did the tool suggest this?" In Part II it becomes the per-problem-loop audit trail.

## 9a. The reasoning-views layer (`reasoning-views.js`) — one state, many views

Realizes vision **Move 1 (documentation-as-exhaust)** + **Move 4 (diagnosis and
education as one act)** as a single display-only layer over the engine's output.
The pattern is **one exam → one reasoning state → many rendered views**:

- `buildExamState()` — a canonical, DOM-free snapshot of the encounter's
  reasoning (captured findings + `V.dxList` with its evidence trail + `V.alerts`
  + `V.nextTests` + token provenance). This is the single object every view
  renders from. It **reads** engine output and never writes it back.
- **SOAP note** (`stateToNoteText`) — a faithful text projection: Assessment
  shows the engine's *why* (`matched / missing / contradicted`), safety alerts
  sit above the assessment, advisory framing is stamped on. Reached via the
  **📝 SOAP Note** button on the report page (`#modalNote`).
- **Casebook** (`deidentifyState` → `casebookAdd` / `showCasebook`) — the same
  state, **de-identified** (PII removed, age capped 90+, name scrubbed from free
  text), stored locally through `storage.js` as a growing library of real
  reasoned teaching cases (`#modalCasebook`). Reachable from the **homepage**
  (📚 Teaching Casebook card) as a standalone study tool. Cases are **grouped by
  leading condition** and **filterable** by search + specialty-domain / sign-token
  chips (pure helpers `casebookFacets` / `casebookFilter` /
  `casebookGroupByCondition`, tested).

**Invariant — anti-fabrication:** a field never entered is omitted, never
rendered as an assumed normal (blankVisit defaults never leak into a note).
**Firewall:** this layer is display-only — no scoring, no differential
generation, nothing feeds back into the engine. Covered by
`tests/reasoning-views.test.js`.

## 9b. Roles, modes & tiers (`roles.js`) — one account, switchable personas

Implements the two-axis model in `docs/ROLES_AND_MODES.md`. **Role** (a
switchable UI/workflow persona: Student / Clinician / Faculty; more `soon`) is
separate from **Tier** (entitlement: free / pro / institutional). `roles.js` is a
DOM-free core: `ENTOPIC_ROLES`, `getActiveRole/setActiveRole/effectiveRole`
(persisted on `CU.role` + localStorage, so one account switches modes),
`getTier/tierLabel`, `canSave`/`SAVE_LIMITS` (free tier caps **saving** only),
and `can()` (capability = role visibility × tier lock). **Learning capabilities
(`ALWAYS_ON`: engine, safety, advisory, offline, KB, casebook, quiz, present) are
never gated** — for any role or tier.

`renderHome()` (`app.js`) is role-aware: a mode switcher strip + per-role **tabs**
+ the active tab's workspace (Student→Study, Clinician→Patients, Faculty→
Teaching, plus shared Casebook/Reference/Account). A first-run **role picker**
(`#modalRolePicker`) asks "who are you here as?"; "Switch mode ▾" is always
available. The exam flow, engine and KB are untouched — roles reorganise the front
door only. The free-tier save cap is enforced at `newPatient()` and
"Save as teaching case" with an honest message (no payment/paywall built —
pricing and real entitlement enforcement are Phase 2). Covered by
`tests/roles.test.js`.

**Rapid Clinical Review Queue** (session 11f, `kb-review.js`): the founder's
fast batch path for signing off provisional entries. `kbReviewItems()` lists
every `NEEDS_CLINICAL_REVIEW` condition with the full attestation surface
(findings, urgency, ICD, summary; urgent first); `kbRapidVerify(name, by)`
flips `review_status`/`icd_status` → `VERIFIED_BY_CLINICIAN` (flags only —
content untouched, test-enforced) and persists through the kb-remote
local-edits overlay so sign-offs survive reloads and bundle loads.
Admin-gated UI (`#modalReview`, Admin-tab card); a sign-off clears the
provisional chips in the KB browser and swaps the About panel's warning for a
dated attestation line (`kbConditionVerified`).

**Super admin** (session 11e): `adminCheckCredentials` (hash-checked pre-set
id/password; changeable via the Admin panel, stored locally as a hash) creates
an ephemeral `adminSessionUser` (never persisted to the users store).
`isAdmin()` short-circuits `getTier()` → institutional and `can()`/cap checks →
everything unlocked at full limits, plus an Admin tab (`homeSecAdmin`: device
stats, local-account management, password change, KB editor, full
export/import) and `kbEditorAllowed` → true. Client-side only — a convenience
lock until Phase-2 backend auth.

Phase-1 refinement (session 11d): the role is chosen **at signup** ("Using
Entopic as" in the setup form → `CU.role`; the picker remains only for legacy
accounts), `roleSessionReset()` isolates role state between accounts on one
device, and each live role has a real headline feature: **Student** — the quiz
(`ui-quiz.js`, vignettes built only from KB criteria or casebook cases, About
notes as explanations, local streak stats) plus uncapped `practice: true`
records (chip-labelled everywhere; free cap counts real records only);
**Faculty** — casebook curation (`casebookAnnotate` / `casebookSetReviewed`,
reviewed badge visible to all roles, review-queue card on the Teaching tab).
Covered by `tests/quiz.test.js` and the casebook-curation tests.

## 10. Honest assessment — strengths and the concrete gaps

### Strengths worth protecting
- Clean separation of raw inputs, engine outputs, and interpretation.
- Deterministic, inspectable, safety-gated reasoning with a visible evidence trail and a glass-box flow map.
- Offline-first with a genuinely comprehensive, clinically literate data schema and finding vocabulary.
- The LLM firewall (engine diagnoses, model only interprets).
- The anonymized-encounter scaffolding — a head start on validation data.

### Gaps that must be fixed for "scalable + trustworthy" (in priority order)

1. **No canonical token registry (root cause).** Five token producers (dictionary, finding-map, KB conditions, free-text regex, measurement auto-derivation) with nothing reconciling spelling, existence, type, or reachability. **Audit: the KB references 512 distinct tokens; only 183 are defined in the dictionary** (Appendix B). Some undefined tokens are legitimately non-lexical (measurement/test tokens), but nothing distinguishes those from typos or dead tokens. This is the direct cause of token collision, undeclared tokens, and unreachable required tokens.
2. **Exclusions silently no-op (verifiable bug).** `applyExclusions` compares snake_case exclusion strings (`"acute_angle_closure"`) by substring against display names (`"Acute Angle Closure Crisis"` → `"acute angle closure crisis"`). Underscores never match spaces, so exclusion rules essentially never fire. Comorbidity suppression is not actually running today.
3. **ICD codes referenced but never populated.** The engine reads `cond.icd`, dxList carries it, there is an ICD coding step — but 0/130 conditions carry a code. The coding page has nothing to render.
4. **Single-list competition.** One ranked differential forces independent, co-existing problems (dry eye + cataract + glaucoma-suspect + convergence insufficiency) to compete for one top slot. This under-serves the common real patient and is the central conceptual limitation.
5. **Universal scoring constants.** Flat +3/+1/−3 across all domains and all tokens — no notion that a given sign is highly specific for one condition but weakly supportive for another. (Your own noted weakness.)
6. **Free-text parsing is brittle.** Regex with no negation handling ("denies pain" still emits `pain`), no guaranteed synonym coverage, English-only.
7. **Persistence ceiling.** `localStorage` is synchronous, ~5 MB, one shared budget, whole-array rewrites on every save. Cannot support onboarding, many patients, multi-device, or backup-by-default.
8. **Auth is a placeholder.** Plaintext credentials in `localStorage`, a hardcoded default password in the setup form. **Irrelevant today** (local single-user, no network, no attack surface) but becomes real the moment there is a backend and multiple users — Part II addresses it there, not before.
9. **No validation data / calibration.** Confidence bands are heuristic; there is no evidence that "80%" corresponds to 80% correctness. This is the single largest credibility gap for academic submission, and the anonymized registry is the intended fix.
10. **UI is full-panel `innerHTML` over global state.** Works, but no reactivity, isolation, or sub-region updates. Modernizable underneath without changing the visible UI.

# PART II — TARGET ARCHITECTURE

## 0. Principles (the non-negotiables)

1. **Keep the UI and the concept.** The 22-step flow, the three-column exam layout, the advisory panel, the flow map, the offline-first feel — all preserved. Users see the same product, hugely improved.
2. **Rebuild the foundations, not the surface.** New token registry, new engine, new KB schema, new backend — all behind the existing UX contract.
3. **Deterministic and inspectable stays.** Every output remains traceable to evidence. The glass box is a feature, not a debug aid.
4. **Evidence before cleverness.** Every clinical assertion (a token→condition weight, a threshold, an exclusion) carries provenance and can be defended in a paper or a patent claim.
5. **Offline-first, sync-second.** The copilot must work with no network. The backend is for onboarding, backup, audit, multi-device, and validation data — never a runtime dependency for diagnosis.

## A. The trustworthy knowledge base

### A.1 Canonical token registry (the backbone)

A single source of truth for the entire token vocabulary. One file/table, every token declared once, with:

- **`id`** — canonical snake_case identifier (the only spelling that exists).
- **`type`** — one of: `symptom` (patient-reported), `sign` (examiner-observed), `measurement` (derived from a numeric threshold), `test_result` (from an investigation), `risk_factor` (history/demographic), `temporal`.
- **`label`** — human-readable name.
- **`aliases`** — natural-language phrases (absorbs today's `token-dictionary.js`).
- **`sources`** — which input path(s) can produce it (symptom chip, finding-map, free-text, auto-derivation, questionnaire). This makes **reachability** checkable.
- **`derivation`** — for `measurement`/`test_result` tokens, the rule that produces them (e.g. `IOP_max > 21`), so the threshold lives with the token, not scattered in the engine.

**Build-time validator** (runs in `loader.js` / CI and *fails the build* on violation):
- Every token used anywhere in the KB exists in the registry.
- Every token is reachable by at least one input source (no dead required tokens).
- No two tokens are near-duplicates (collision guard).
- Every `finding-map` output and every auto-derived token is a registered token.

This one change eliminates gaps 1, and makes 5–6 tractable. It is the highest-leverage work in the whole plan.

### A.2 Condition schema v2

Extend the condition object (keeping `req`/`sup`/`con` intact) with:

- **`id`** — stable identifier (never the display name). All cross-references (exclusions, hierarchy) key on this. Fixes gap 2.
- **`codes`** — `{ icd10: "...", snomed: "..." }` on every condition. Fixes gap 3. (Two connected MCP tools — *ICD-10 Codes* and clinical terminology sources — can be used to populate and validate these during KB authoring.)
- **`weights`** — replace flat scoring. Each token reference carries a strength grounded in evidence, expressed as a **likelihood ratio** (or a sensitivity/specificity pair) for that token *given that condition*. This is what makes scoring "based on scientific principles" (see C.3).
- **`relations`** — explicit, ID-keyed: `excludes` (mutually exclusive), `parent`/`child` (hierarchy: e.g. "NPDR" → "moderate NPDR"), `co_occurs_ok` (do **not** suppress; comorbid by design). Fixes gaps 2 and the comorbidity-suppression failure mode at once.
- **`evidence`** — provenance: `{ citations: [...], grade: "A|B|C", source: "DEWS II | AAO PPP | ...", reviewed: "YYYY-MM", reviewer: "..." }`. This is what makes the KB *trustworthy* and *publishable*, and it directly feeds your JMIR / npj / PLOS submissions.

### A.3 Evidence governance (what makes it "unbeatable yet reliable")

- **Grading scheme** — adopt a standard evidence hierarchy (e.g. Oxford CEBM / GRADE) so every weight and threshold has a defensible level. "Unbeatable" comes from *coverage + provenance*, not from volume alone.
- **Versioned KB bundles** — the KB is content, not code. Version it independently (semver), sign it, and serve it from the backend so KB updates ship without redeploying the app. Clients cache the latest signed bundle and keep working offline.
- **Peer-review workflow** — KB changes go through review (author → clinical reviewer → merge), with the `reviewed`/`reviewer` fields enforced. This is your defense against silent clinical drift and is exactly what reviewers and regulators want to see.
- **Domain-by-domain authoring discipline** — continue your established one-domain-at-a-time rewrite pattern, now against schema v2 and the registry validator.

### A.4 Reliability engineering

- **Golden-case suite** — grow your 12 clinical simulations into hundreds of labeled vignettes (input → expected active problems + expected safety flags). Run on every KB or engine change.
- **Regression + calibration testing** — assert that (a) known cases still resolve correctly, and (b) confidence is *calibrated*: across the labeled set, cases the engine calls "80%" are correct ~80% of the time. Calibration is the number that earns clinical trust and anchors a strong paper. Fixes gap 9.
- **Coverage/reachability reports** — surface unreachable tokens, conditions no case exercises, and tokens no condition uses.

## B. The continuous, independent-looping engine

This is your "looping conditions for independent identification of problems and independent solving of those," made concrete.

### B.1 From one ranked list to concurrent problem loops

Today: collect tokens → score all → one sorted list. Target: collect tokens → **partition into independent problem foci** → run **one independent diagnostic loop per focus**, concurrently. The output is *N* independent working problems, each with its own confidence and its own refinement state — not one list where they fight.

> **Implemented (2026-07-04, first bounded version):** `computeProblemFoci(dxList)` in `js/engine.js` partitions the scored differential into independent problems **by clinical domain**, each with its own lead condition, confidence band, within-focus alternates, and per-problem "next check" (the lead's top missing evidence). It is written to `V.problemFoci` and rendered as a **"Working Problems"** section in the advisory panel (above the flat differential, which is retained). This is a **deterministic presentation layer over the existing scoring** — it deliberately does *not* yet implement the per-focus state machine (B.3) or change scoring, so it carries zero regression risk and keeps `V.dxList` intact. The state-machine/value-of-information loop (B.3) remains the next step. Covered by `tests/engine-problem-foci.test.js`.

### B.2 Problem-focus clustering

After token collection, group tokens into **foci** by anatomical/functional domain and co-activation (surface, cornea, lens, glaucoma/disc, retina/macula, neuro, binocular, refractive). A patient with dry-eye tokens *and* disc/IOP tokens *and* convergence tokens yields **three foci**, each seeded independently. Clustering rules are explicit and inspectable (and themselves testable).

### B.3 The per-focus loop as a state machine

Each focus runs an independent hypothesis tracker with states:

```
SUSPECTED → INVESTIGATING → CONFIRMED
                         ↘  REFUTED
                         ↘  PARKED (insufficient evidence; watch)
```

On every data change, each active loop:
1. **Re-scores** its candidate conditions against current tokens (using the evidence-graded weights).
2. **Identifies the discriminating evidence** — the single test/finding whose result would most change the posterior among its live candidates (a value-of-information heuristic: "what should I check next *for this problem*"). This produces a **focused, per-problem nudge**, far more clinically useful than today's generic ones.
3. **Transitions state** when evidence crosses thresholds (confirm/refute) or stalls (park).
4. **Emits its own evidence trail and confidence**, independent of the other loops.

Loops are independent: confirming glaucoma does not suppress the dry-eye loop; parking the neuro loop does not affect the refractive one. This directly resolves gap 4 and matches the clinical reality of multi-morbid patients.

### B.4 Scoring upgrade (per-domain, then Bayesian)

- **Phase 1 (your existing plan):** per-domain weight profiles instead of universal constants (e.g. Neuro 0.80/0.20, Refractive 0.45/0.55). Ships quickly, removes the arbitrary-constant weakness.
- **Phase 2 (target):** each token carries a **likelihood ratio** per condition; a focus computes a posterior from a domain prior updated by the LRs of observed tokens. This is transparent, literature-anchored, calibratable, and is a strong, defensible basis for both publication and patent claims. Confidence becomes a real posterior, not a heuristic band.

### B.5 The safety layer stays hard, independent, and un-suppressible

The decision-tree gates and alerts (Stages 5 & 10 today) remain **hard-coded rules that run outside the probabilistic loops and can never be suppressed by scoring or exclusions**. Red flags (RAPD, flashes+floaters, IOP >40, hypopyon, rubeosis, bilateral disc edema, sudden vision loss) always fire. Safety is not probabilistic. This is preserved exactly.

### B.6 The flow map becomes the per-loop audit trail

The existing layered flow map generalizes: one glass-box trail **per problem loop**, showing that loop's tokens → candidates → discriminating evidence → state → confidence. This is the honest, inspectable answer to "why this problem, why this confidence, what next" — and it is a strong figure for a methods paper.

## C. Scalable, stable backend and onboarding

### C.1 Local-first, sync-second

Keep the app fully functional offline. Change the persistence engine, not the workflow:

- **Replace `localStorage` with IndexedDB** (async, hundreds of MB, indexable) as the local store. Fixes gap 7's ceiling and unblocks many patients per device.
- **Add a sync engine**: local writes go to an outbox; when online, they sync to the backend; conflicts resolved by last-writer-wins per field or a simple version vector (visits are append-mostly, so conflicts are rare). The clinician never waits on the network to run an exam.

### C.2 Backend recommendation: Supabase

Supabase (already in your connected tooling) is a natural fit and gives you the whole backend in one managed platform:

- **Postgres** — relational store for `clinics`, `users`, `patients`, `visits`, `kb_versions`, `encounters` (de-identified). Real queries, real indexes, real backups.
- **Auth** — hashed credentials / OAuth / magic links; kills the plaintext-password issue (gap 8) properly, at the layer where it actually matters.
- **Row-Level Security (RLS)** — enforce multi-tenancy in the database: a user sees only their clinic's patients. This is the correct place for that guarantee, not the client.
- **Realtime** — optional live sync / multi-clinician collaboration (your v2 roadmap item).
- **Edge Functions** — server-side KB-bundle signing, registry ingestion, and the anonymization pipeline.

### C.3 Onboarding, roles, multi-tenancy

- **Entities:** `clinic` → `users` (roles: optometrist / ophthalmologist / technician / admin) → `patients` → `visits`.
- **Onboarding flow:** clinic sign-up → admin invites users → role-scoped access. RLS enforces isolation server-side.
- **Roles gate capability** (e.g. who can finalize a diagnosis vs. record findings), matching real clinic hierarchy.

### C.4 PII separation and the validation pipeline

- **Split PII from clinical data.** Patient identifiers live in an encrypted, access-controlled table; clinical encounters reference patients by opaque ID. Analytics and the registry never touch PII. Your `blankPatient`/`blankVisit` split already models this — formalize it at the DB boundary.
- **Consented anonymized registry → validation dataset.** Promote `buildAnonymizedEncounter` into a server pipeline (opt-in, consented, de-identified per your `getAgeBracket`/token projection). This dataset does double duty: it **calibrates the engine** (A.4) and it **is the clinical-validation evidence** for your papers — closing gap 9, your biggest credibility gap.
- **KB delivery:** signed, versioned bundles from the backend; clients cache and run offline; updates propagate without app redeploys (A.3).

### C.5 Observability and audit

- Structured engine logs (you already keep `engineLog`) shipped to the backend for audit.
- Full audit trail on clinical records (who saw/edited what, when) — required for any real clinical deployment and for regulatory posture.
- DB migrations versioned alongside KB versions.

# PART III — MIGRATION PATH (phased, non-disruptive)

Sequenced so the UI never breaks and each phase ships value. This mirrors your established discipline: clean rewrites over patches, one bounded piece at a time, validated before advancing.

**Phase 0 — Instrument and freeze.** Lock the current UI contract. Stand up the golden-case suite against today's engine so every later change is regression-tested.

**Phase 1 — Token registry + validator.** Build the canonical registry (A.1), migrate the three token layers into it, wire the build-time validator into `loader.js`/CI. Fixes gap 1; surfaces every dead/colliding token. *No UI change.*

**Phase 2 — KB schema v2.** Add `id`, `codes`, `relations`, `evidence` to conditions; fix exclusions to key on IDs (gap 2); populate ICD-10/SNOMED (gap 3). Keep `req`/`sup`/`con`. Re-author domains one at a time against the validator. *No UI change.*

**Phase 3 — Engine v2 (loops + calibrated scoring).** Introduce focus clustering and per-focus state machines (B) behind the existing advisory panel; ship per-domain weights, then LR-based scoring; add calibration testing (A.4). The advisory panel now shows independent problems instead of one list — same panel, better content. Safety layer unchanged (B.5).

**Phase 4 — Local-first persistence.** Swap `localStorage` → IndexedDB + outbox (C.1). *No UI change*; removes the storage ceiling.

**Phase 5 — Backend + onboarding.** Stand up Supabase (Postgres/Auth/RLS), sync engine, roles, multi-tenancy (C.2–C.3). Real auth replaces the placeholder at the layer that matters (gap 8).

**Phase 6 — Validation pipeline + KB delivery.** Consented registry → validation dataset → calibration + papers; signed versioned KB bundles served from backend (C.4). Closes gap 9.

Each phase is independently shippable and independently valuable; none requires a visible UI rewrite.

# APPENDIX C — Glossary

- **Token** — an atomic clinical fact (symptom, sign, measurement, test result, risk factor, temporal marker) the engine reasons over.
- **Route** — a clinical pathway/domain the engine evaluates (glaucoma, retina, neuro, …), used to avoid scoring the whole KB.
- **req / sup / con** — a condition's required / supportive / contradicting tokens; the core scoring triad and the patent's central idea.
- **Gate** — a hard clinical override that surfaces specific conditions regardless of scoring (safety net).
- **Focus (problem focus)** — a cluster of tokens representing one independent clinical problem; each runs its own diagnostic loop (Part II.B).
- **Evidence trail / flow map** — the glass-box record of how the engine reached a result; the transparency differentiator.
- **Likelihood ratio (LR)** — evidence-based measure of how much a token shifts the probability of a condition; replaces flat scoring weights in Part II.
- **Local-first** — data lives and works on-device; the backend syncs, backs up, and audits, but is never required to run an exam.
